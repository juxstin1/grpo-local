## Blocking defects in the older endpoint pipeline

1. **Candidate code can manufacture a pass or read the answer key.**
   `evals/graders.py:153–162` gives the candidate process a JSON job containing
   expected outputs. `_run` at line 206 accepts the last JSON-looking stdout line.
   Two harmless invented candidates passed without solving the problem: one
   printed a constant `passed/total` receipt and exited; another read the expected
   values from its own job file. Python `-I`, a temporary directory, and a reduced
   environment do not create an evaluator trust boundary. The same module supplies
   SFT collection grading (`sft/collect.py:194`). This demonstrates a capability,
   not evidence that saved model outputs exploited it.

2. **Invalid and unrelated attempts become scores.**
   The actual summary function in `evals/eval_runner.py:513–554` produced accuracy
   `0.0` for an invented all-request-error run and `2.0` for two foreign successful
   IDs against a one-item selected set. It skips invalid rows but retains the full
   denominator, does not constrain IDs, and does not deduplicate attempts.
   Resume at lines 438–446 checks item/attempt and budget without binding model,
   dataset, prompt, sampling, or grader identity. This makes reused output folders
   unsafe for comparisons.

3. **Other endpoint false accepts are reproducible.**
   A stdin candidate that printed the expected answer and then raised an exception
   passed; a stdin task with zero tests passed. `run_stdin` never checks return code
   and returns success after an empty loop (`evals/graders.py:221–235`). The multihop
   grader accepted both a retracted correct answer and an earlier answer followed
   by a blank final `ANSWER:` line (`:99–115`). These are separate from the repaired
   `ops/reward_contract.py` path.

4. **Math task IDs collide across different questions and answers.**
   The pool has 43 excess UID occurrences: 23 duplicate-ID groups containing 66
   rows. Every group has multiple prompt texts and multiple answers. These are
   identifier collisions, not just repeated identical examples. The collector
   stores prompts by UID (`sft/collect.py:162`) and later retrieves them by that UID
   (`:174`); a collision can substitute another problem's prompt while retaining
   the original task's grader. Stats and per-task caps also share that key. The
   same pool contains 128 excess exact prompt occurrences across its sources.

5. **The exclusion registry omits most public endpoint evaluation roots.**
   `sft/collect.py:45–59` protects only `post_cutoff_v1_5pb.json` plus discovered
   sealed roots. **186 of the full public set's 191 roots are absent from the
   small-file exclusion list**: 112 math and 74 code roots. A missing sealed
   directory silently contributes no exclusions. Trainer and salvage reuse this
   function. No exact public-evaluation root overlap was found in the inspected
   training pools, local SFT collections, or hosted dataset. This is a demonstrated
   protection gap, not demonstrated contamination; fuzzy duplicates and private
   overlap were not rechecked.

6. **Post-cutoff code status is heuristic, and code tests are visible examples.**
   All 87 public code items use `date_basis=leetcode`. `date_record` labels a late
   first-activity upper bound as `post` (`prepare.py:107–120`). The fixture confirms
   that classification; a late upper bound cannot establish a late publication.
   The additional problem-ID filter is also heuristic. Do not label these items
   proven unseen from this metadata.
   All 87 use statement examples as tests: 36 have two, 49 have three, one has
   four, and one has five. Thus **85/87 have only two or three visible cases**.
   Accepted-solution agreement validates those examples, not general correctness.

7. **Legacy LCB candidate executions share a file.**
   `evals/eval_runner.py:115–124` writes and executes `.tmp/lcb_work/solution.py`
   while grading can run concurrently (`:569`). This is a source-level race;
   this review did not reproduce it or determine historical affected attempts.

## What the saved scores mean

All 39 accessible `evals/results/**/*.summary.json` files lack dataset/model/grader
digest fields and a budget field; 11 omit attempt counts. Twelve contain two
attempts per expected item while naming the solved count `pass4_items`. The current
source adds budget but still hardcodes that label. These summaries do not establish
an exact served-weight identity or a reproducible current ranking.

The Qwen3.5-2B BFCL, When2Call, and legacy holdout summaries report zero accuracy
with no graded item entries. `docs/state.md:21–23` already identifies these as
request-error runs. The LCB summary covers 28 of 30 IDs. They must not be interpreted
as clean model baselines. Filesystem dates place the 39 summaries in September
28–30; those dates alone are not execution timestamps.

When2Call's implementation checks call/no-call presence (`eval_runner.py:202–208`),
not correct arguments or completed actions. Its metric must be named accordingly.

Tau2 is a distinct evaluation: its source marks insufficient valid trials as
missing and requires exact settings for resume. However its comparison key list
(`tau2-bridge/run_tau2.py:290`) omits agent temperature, thinking, and max steps,
despite recording those settings. No accessible Tau2 result directory was found.
Its retail mode can use an external language-model judge; the older endpoint
graders reviewed above are Python functions, not a Claude judge.

## Provenance and coverage limits

- Both pool manifests hash logical LF serialization while the current files have
  different raw hashes. Logical hashes match exactly; this is a serialization
  mismatch, not proof of changed task content. `prepare.py:421–425` hashes a string
  before Windows text-mode writing. Future receipts must name raw bytes explicitly.
- `latest.json` contains combined math/code results but only code provenance.
  The older `prepare-20260928T223424Z.json` retains 29 MathArena source revisions.
  Partial rebuilds carry previous results without merging their provenance. No
  item-level license or source-revision fields occur in the endpoint pools/sets;
  a source registry can supply these, but the relationship must be explicit.
  This review did not revalidate upstream license terms or publication dates.
- Hosted training metadata reports 497 episodes, 482 roots, 25 hinted episodes
  admitted, and two hint texts stripped. These are manifest claims, not a fresh
  trajectory review. 554/617 rows name `deepseek-ai/DeepSeek-V4-Flash-0731` as teacher;
  seven teacher names appear overall. Different teacher names do not by themselves
  establish diverse task structures or demonstration quality. The manifest explicitly
  lacks historical task-spec, fixture, and output-artifact hashes, preventing a
  complete retrospective replay from this package alone.
- Synthetic multihop uses one world and two chain templates in the current small
  set. Different names/seeds can prevent exact fact reuse without demonstrating
  transfer to different reasoning structures. Five items per bucket also means
  one item's outcome moves item accuracy by 20 percentage points.
- The four new public contract tasks cover constrained refactoring, approved
  decision extraction, revised-order totals, and scoped document edits. They do
  not yet test general repository repair, tool recovery, consequential ambiguity,
  or broad multi-turn work. More rows copied from those four roots would not close
  those coverage gaps.
- `runs/grpo-q4` points to `L:/Project-Offloads/grpo-local/runs/grpo-q4`; the target
  was unavailable during this review. No current claim about those archived
  training/evaluation records is made here. This blocks their fresh inspection,
  not the offline repairs above.
